# Architecture Decisions

Status: accepted sample design decisions for this architecture; infrastructure values and operational SLOs remain configurable before deployment.

## ADR-001 — Boundaries and hosting
Use AWS S3 as the reference object-store deployment, keeping actual buckets, cloud region and credentials unspecified. Use one Databricks catalog with bronze, silver_restricted, silver, gold and ml schemas. Separate restricted and curated Silver to make different access policies visible. Separate model boxes represent ownership/governance boundaries, not extra workspaces.

## ADR-002 — Source truth, extraction and replay
PostgreSQL owns customer/order/item/product state. Source timestamps are UTC-aware and soft deletes are explicitly exported. Extract a repeatable snapshot from a read replica with a persisted high watermark and five-minute overlap. Read [previous watermark - overlap, run cutoff); use deterministic updated_at and stable identifier order. Advance the cursor only after sink validation and successful commit. Files are immutable by batch identifier; retries reuse that identifier. Proposed cadence: orders/items every 15 minutes, customers hourly, products hourly, partner daily. Raw landing retention 30 days, Bronze 90 days, Kafka 7 days are sample starting policies requiring operational review.

## ADR-003 — Streaming and reconciliation
Kafka customer_events envelope includes explicit event_id/type/customer/session/product/order/time/version fields. Partition by customer_id; preserve topic/partition/offset in Bronze. Consumer uses its own protected checkpoint directory and Delta sink. Silver deduplicates event_id with two-hour watermark, validates event types and joins a restricted customer identity map. Anonymous/unresolved identities are quarantined, never silently assigned. Late arrivals beyond the live watermark are recovered by nightly Bronze replay. No global exactly-once claim across PostgreSQL, Kafka and applications; idempotent business keys and replay are required.

## ADR-004 — Privacy and identity
Direct names, email, phone and street address remain in source, landing, Bronze and Silver Restricted only. Normalize email using lower/trim and phone by retaining digits; this sample does not claim global E.164 validation. Create stable customer_key from a secret-peppered source customer ID; email_hash from normalized email plus a separately scoped secret. Secret values are runtime inputs held by a secret service, never document literals. Hashes are pseudonymous, still classified PII. Do not merge customers solely by email. customer_360.customer_identifier derives from email_hash, while all joins use customer_key. Restricted identity map links source ID to customer_key and key_version for controlled deletion/rekey workflows. Analytics roles receive only approved schemas/views. Encryption keys, secret policies, grants and physical retention jobs are design requirements, not provisioned settings.

## ADR-005 — Quality, keys and deletes
Bronze preserves source fields, including malformed strings; Silver parses, validates and deduplicates. Reject references include source key/file/reason rather than copying PII. Latest-record selection occurs before soft-delete filtering so deleted versions do not resurrect older rows. Current-state Silver refresh uses deterministic snapshot replacement semantics in this sample; production incremental MERGE must include tombstone handling. Downstream current-state marts are rebuilt from consistent Silver snapshots. Historic raw retention and subject-rights purge requirements require explicit privacy operations, not just soft deletion. PostgreSQL PK/FK is design for source enforcement; Delta keys are informational plus pipeline checks.

## ADR-006 — Business grains and metrics
Order item amount = quantity * unit_price. Only completed orders contribute to sales. Metric is gross merchandise revenue, excluding tax, shipping, discounts and refunds not modeled in this first sample. Group sales by UTC date and currency; never add amounts across currencies. customer_lifetime_value means realized historical spend, not predictive valuation. Product enrichment resolves a single authoritative partner record per product_code before joins, avoiding revenue multiplication. Gold products combine multiple curated datasets; customer_activity_summary combines batch customer attributes and behavioral event history.

## ADR-007 — ML scope
Model a simple logistic churn inference workload with feature snapshots, versioned coefficient artifact, approved flag, training cutoff and currency. Features use data strictly before as_of_date, and recent activity spans 30 complete days. Coefficients must correspond to the exact unscaled features in the contract. A trained artifact must be supplied or trained and validated before deployment; no coefficients, model accuracy or training execution are invented. Scoring has explicit feature-to-probability lineage. Consent-filtered output can be consumed by application activation; no raw contact data is exported.

## ADR-008 — Runtime guarantees and operations
Separate scheduler/control dependencies from data-attribute lineage. Persist schedule, task dependencies, failure gates, retry limits and ownership in processor metadata and pipeline_operations.md. Keep run audit and cursor contracts explicit. Runtime retries: 3 with a 60-second minimum interval (ADR-015); stop Gold on failed upstream quality gates. Monitor freshness, volume drift, rejects, duplicate keys, schema drift and late-event reconciliation. Job configurations, notebooks and local tests are now implemented; Databricks grants, buckets and live deployment remain unprovisioned.

## ADR-009 — Retention-safe source baseline
Hourly/15-minute overlap extracts alone cannot rebuild all current records after Bronze retention expires. Each PostgreSQL synchronization therefore performs a daily full source snapshot at 00:30 UTC (full_snapshot input), alongside incremental runs. Block Silver snapshot publication if the latest complete baseline is older than 48 hours. Deletions must be source soft-deletes or explicit CDC tombstones. Stream history older than Bronze retention is preserved in Silver; nightly reconciliation merges the retained Bronze horizon into historical Silver, not a full replacement. Retention/purge policy must propagate to Silver separately.


## ADR-010 — Customer implementation and consistent publication
The first executable vertical slice is PostgreSQL customers → immutable JSONL landing → raw_customers Delta → normalized_customers / customer_identity_map / silver_customers Delta, with reference quarantine, audit and cursor commit. Implement with Python, psycopg server-side extraction, boto3 conditional S3 writes and PySpark/Delta. The sample source workload is batch; Kafka streaming remains a later coherent milestone.

Each customer run has an immutable request (batch_id, aware UTC start/end, full_snapshot). A completed landing manifest pins file checksum, row count and extraction time; retry reads the completed file without re-querying mutable PostgreSQL. Incomplete extraction files are never discoverable inputs. Source extraction is REPEATABLE READ READ ONLY, UTC, ordered updated_at/customer_id, window lower bound minus five minutes and exclusive end. Source timestamps are required and source identifiers come from PostgreSQL BIGINT canonical text. Runtime rejects noncanonical IDs in imported raw data rather than conflating raw partitions.

Use an S3 conditional-create writer lock for the whole customer run and ETag compare-and-swap for the cursor. Locks have no unsafe automatic expiry; a crashed owner requires operator recovery after confirming its job stopped. Max concurrent runs = 1, with three orchestrator retries reusing the batch ID. The lock is always released on normal success/failure. Landing completed manifests and successful publication manifests are immutable. Delta append checks the batch ID under this lock, including restart after write-before-response; empty batches are still represented in manifests.

The customer_pipeline_publications contract and commit_customer_publication processor record Delta versions for all three customer snapshot sinks plus raw version and the baseline batch. The existing ingestion_cursors.checkpoint_uri points to this manifest. Readers must capture one cursor, load its immutable manifest, and time-travel all tables to these versions. Atomic per-table overwrite is not treated as a multi-table transaction. Candidate latest table versions can be visible to the writer only; downstream jobs consume the manifest and retain the prior publication on failure. Restrict direct latest-table consumer access. This avoids depending on catalog-managed multi-table transaction features. Delta version retention must exceed the lifetime of active publication manifests; vacuum cannot remove the active versions.

Silver rebuild reads only raw batch IDs in the committed predecessor chain since its most recent full baseline, plus the current batch. A current full snapshot resets that set, including empty full snapshots. Baseline freshness is <=48 hours relative to run cutoff; future or regressing cutoffs fail. Failed candidate batches remain Bronze evidence but are excluded from later epochs. A full snapshot is authoritative for the customer set at its cutoff; source deletes must still be soft deletes under ADR-009.

Quarantine all malformed raw rows in the selected epoch with the modeled reference-only reason INVALID_CUSTOMER. Publication gates only latest invalid records plus unorderable timestamps/IDs. A later valid source version resolves earlier well-ordered invalid versions. Bad timestamps or identifiers require a corrected full baseline. Rank before tombstone filtering using the modeled updated_at/ingested_at/batch_id ordering. Conflicting payloads for an identical version/order key fail instead of nondeterministic selection. Duplicate identical rows collapse. Reject duplicate customer IDs within one landing batch (source PK violation). Marketing consent retains the existing invalid→false rule; email validation remains the modeled minimal @ syntax check.

The publication manifest is written after all sink validations and before cursor CAS. Successful cursor CAS is authoritative even if audit logging subsequently fails; retries repair the success audit. Run audit is one immutable terminal manifest per batch; pre-commit failed attempts use distinct attempt IDs. Shared Bronze/quarantine/audit/cursor processors stay partially implemented until their other modeled paths are delivered. Secrets are injected in memory, never manifests, logs or configuration files; test peppers are synthetic.

Customer adapter sizing: the first sample implementation supports at most 64 MiB JSONL per extracted batch, failing before publication if exceeded. A partitioned manifest/multipart extractor is a future architectural extension. Publication previous_batch_id explicitly links committed epochs. Empty first publication requires full_snapshot=true. Identity hashing executes in a Python UDF closure so secret literals are not placed in SQL plans; Spark event/driver logging still requires restricted access and secret redaction.

Customer deployment specialization: the paused Databricks job uses max_concurrent_runs=1 and three Lakeflow-managed retries with a 60-second minimum interval. This first job does not promise exponential delays; ADR-015 extends this same minimum-interval retry policy to the complete bundle. Runtime provisioned grants, storage encryption, publication-aware consumer access, retention and live integration validation remain deployment gates. Local Spark/Delta integration and adapter simulations are separate evidence from deployed tests.


## ADR-011 — Executable event pipeline
Kafka Bronze uses explicit JSON string envelope fields plus broker topic/partition/offset and server ingestion time. Invalid envelopes remain as null/malformed contract fields with broker provenance; the source broker retains original bytes for its configured replay horizon. The stream does not invent an event ID. Live Silver filters syntactically invalid/time-poisoning rows before a two-hour event-time watermark and event_id state deduplication; nightly Bronze reconciliation quarantines those filtered records and recovers late/unresolved events. Product behavior requires nonempty session_id and a parseable product_id; order lifecycle requires parseable order_id. Events more than five minutes ahead of ingestion time are quarantined to avoid poisoning the watermark. This sample records broker provenance, not a second opaque raw-message payload.

Each Silver microbatch pins the current published customer identity map. Anonymous/unresolved identities are quarantined. A serialized events writer lock covers both live and replay merges. Delta insert-only MERGE on event_id preserves historical events and is retry-idempotent. First accepted event ID owns its immutable business payload; a later conflicting payload is quarantined, never overwritten. Nightly replay ranks candidates by the modeled ingestion time and broker coordinates before acceptance. Recovery retries an uncommitted microbatch from its checkpoint; raw Bronze is already durable. Live syntax-rejected/late rows are accounted during nightly reconciliation rather than lost.

All runtime SQL mappings are exported from Beyond Entity and executed as staged Spark SELECTs over isolated temporary views. INSERT mappings select explicitly ordered target columns before a controlled Delta writer; processor virtual tables are not external databases. Existing attribute lineage remains the contract. Tests cover streaming checkpoint restart and batch reconciliation separately; Kafka connectivity is deployment validation.


## ADR-012 — Remaining batch/Gold/ML implementation protocol
Extend ADR-010 publication to source-commerce, partner, Silver-commerce, Gold and ML epochs using pipeline_table_versions and pipeline_epoch_dependencies in job orchestration. Each pipeline cursor's checkpoint_uri points to immutable version/dependency rows; source_table may name a logical pipeline group. All downstream code reads versions from one committed manifest. Preserve the prior publication on validation or write failure. Serialize publication per pipeline, and serialize all shared quality_quarantine writes with a common quarantine lock. Streaming live/replay share the events lock. Customer quarantine writes participate in the common lock too.

Orders/items are extracted every 15 minutes; products on the hourly due subset. First extraction and daily 00:30 UTC source-commerce run are full baselines of all three. Immutable per-source landing completion metadata records fields/count/checksum. Rebuild source table horizons from the latest successful full baseline plus committed incremental batch IDs; empty baselines remain meaningful. PostgreSQL source adapters use bound queries under read-only repeatable-read; the grouped commerce source reader uses a shared connection transaction. Cutoff windows remain source updated_at filters, not historical time-travel queries; frozen features are required for historical ML evaluation. A 48-hour full baseline gate applies to source-commerce. Customer-only scheduling remains ADR-010. Each source has the same 64 MiB per-batch limit as the first customer sample adapter.

Partner delivery is a complete authoritative partner catalog CSV with product_code, brand, supplier_region, effective_date and partner_id. file_checksum is metadata of the delivery envelope (expected SHA-256 over the original CSV bytes), not a self-referential CSV column. Verify the supplied digest before writing landing/Bronze. Require one configured authoritative partner, unique normalized SKU in a delivery, valid dates and nonempty fields. Partner full snapshot publication replaces that partner's current catalog; block daily Silver refresh if delivery exceeds 48 hours. Missing optional enrichment remains a left join; absent source publication is not silently treated as an empty successful delivery.

Execute Beyond Entity's staged transformation SQL with named parameter bindings. Explicit target contracts enforce casts, required fields and key grains. Products/orders must use a supplied nonempty approved currency set; reporting currency must belong to it. Reject amount/aggregate overflow rather than null or rounded overflow publication; modeled amounts retain DECIMAL(18,2). Validate latest source rows plus unorderable versions; quarantine references include unresolved current joins, while historical resolved rejects do not permanently block release. Latest tombstones are handled before parent joins. Source identifiers are canonical BIGINT strings. Revenue reconciliation compares completed-order line amounts to per-currency Gold totals before publication.

Gold reads a pinned Silver-commerce publication, the customer publication used by that Silver epoch, and a pinned event Delta version captured at refresh start. Snapshot_date/as_of_date cutoffs are immutable request inputs. Dated feature snapshots and score partitions are immutable by modeled grain; identical retries are allowed, conflicting recomputation requires an explicitly approved backfill decision. Model artifacts must be supplied with finite coefficients, approved=true, stable model_version, currency and training_cutoff before scoring date. Registration is immutable by model_version. Tests use explicitly synthetic coefficients and claim no trained model accuracy.

Activation/export are controlled object-storage handoffs, not unsolicited sends to external people or services. Before export, re-read the current customer publication and filter current consent. Replace the active activation handoff so withdrawals are retracted; old exports are subject to coordinated privacy purge. Reports honor start-inclusive/end-exclusive date bounds. Export manifests preserve the modeled explicit row fields; no direct contact fields leave curated zones. Missing approved production model or cloud configuration prevents deployment execution, not implementation of the configurable code paths.


## ADR-013 — Feature freeze and object handoff details
The ML writer records a frozen feature-partition pointer under frozen/churn_feature_snapshots/<as_of_date>/<currency>.json using the existing pipeline_table_versions contract. This records empty partitions too. Later runs must match the entire frozen partition; added, removed or changed feature rows require an explicit backfill decision. Scores are immutable by their modeled key and payload (scored_at is retry metadata). Model registration rejects conflicting reuse of model_version and validates finite coefficients and provenance URI; approval is a trusted release input, not an AI-generated claim.

Object handoffs retain exact numeric values: generic JSON number contracts preserve Spark integral/decimal numeric types rather than coercing financial decimals to binary floating point. Export JSONL is capped at 64 MiB in this sample, like bounded source adapters. Reports are immutable per export run. Activation uses one conditionally replaced active handoff object and checks the current customer publication every invocation, including retries, so a consent refresh can retract a previously exported customer. The caller must trigger refresh after a new customer publication; orchestration includes an hourly activation refresh against the latest approved score publication. Historical raw/features/scores still require the separate coordinated privacy purge procedure. No external email/API delivery is performed by these exports.


## ADR-014 — Application source adapter implementation
The two proposed HTTP endpoints use a FastAPI application factory requiring a deployment-supplied credential verifier. It must derive a trusted customer principal from authenticated credentials; no permissive default or client-asserted customer_id is accepted. Profile updates require matching subject ownership or the explicit customer_profile_admin service role. Endpoint validation rejects extra fields, malformed UUID/timestamps and invalid payload types; behavior kinds remain product_viewed/product_added_to_cart. Kafka publication uses acks=all and idempotent producer configuration, waits for delivery acknowledgement, and returns 503 on missing/failed acknowledgement. Delivery is still at-least-once across API retries; event_id remains the downstream dedup key.

The modeled order processor operates on an existing order, optionally within the operational caller's surrounding creation transaction. It does not invent an order-creation schema outside the modeled UPDATE/outbox contract. order_created requires an existing created order and new_status=created; order_cancelled allows created/paid→cancelled. completed/cancelled are terminal for this cancellation flow; refunds/payment transitions are outside this processor. Lock the order row, enforce one event per order/kind, and atomically update status plus insert its outbox event. Retry of the same event ID and matching order/kind is idempotent; conflicting reuse is rejected.

Outbox relay locks pending rows with FOR UPDATE SKIP LOCKED, publishes using customer_id as Kafka key, and marks only broker-acknowledged events published. Increment publish_attempts for each observed relay attempt, including handled delivery failures. Its increment and acknowledgement update commit with the relay transaction; a process crash can leave an unrecorded attempt and can produce a duplicate event, handled by event_id dedup. Do not claim exact attempt accounting across process/broker failures. Failed delivery remains unpublished and retryable. Connections, auth verification, broker credentials and HTTP hosting remain deployment bindings; implementation tests simulate those boundaries.


## ADR-015 — Complete scheduling and live activity cutoff
Hourly activity needs a timestamp cutoff rather than the daily as_of_date boundary. Add activity_cutoff to aggregate_customer_activity and use it in the existing event_time filter, preserving all aggregation lineage. Daily Gold supplies as_of_date midnight UTC; hourly live activity supplies its triggered run cutoff. Both write the existing customer_activity_summary Delta table under a common activity lock. Hourly readers pin a separate activity_live epoch; daily Gold/ML pin the version in the complete Gold epoch, so live partial-day rows cannot leak into dated features. Delta overwrite/version retrieval is serialized for this shared table.

Customer/source cadence uses the scheduled trigger time for due decisions and actual job start for extraction cutoff. Daily baseline selection also catches up if the previous full baseline belongs to an earlier date after 00:30 UTC, rather than missing a day after a queued job delay. Products are due hourly, with catch-up if their last extract is older than an hour. The daily DAG runs Silver and event reconciliation before Gold; ML depends on Gold, activation on ML, reports independently on Gold. Continuous Bronze and Silver streams use distinct checkpoints; first Kafka startup defaults to earliest retained offsets and failOnDataLoss=true. Outbox relay is a retryable minute job; live activity and activation refresh hourly. Partner delivery and model release are explicit parameterized jobs, not fabricated scheduled inputs.

All configured schedules/continuous triggers remain PAUSED until deployed deliberately with environment bindings. Job task retry budget is three with a 60-second minimum interval; customer/source request persistence preserves batch identity during repairs. Source completeness/freshness and model artifact checks fail closed. Model registration and partner delivery parameters must reference actual approved inputs supplied at execution.
